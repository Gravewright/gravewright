# Gravewright 0.3.2 — Alpha

## Changes

Gravewright 0.3.2 brings campaign preparation outside the table, shared progress
clocks and staged clues, expanded PDF sheet authoring and MapBuilder integration.
These notes describe the prepared source version since `0.3.1`. A published tag,
download and completed platform checks are separate release steps.

### Campaign manager and preparation

- **Manage campaign** on a campaign card opens the GM workspace before entering
  the table. Campaign GMs, including co-GMs, use the same journals, quests,
  actors, system sheets, items, scenes, file library, audio, cards, compendiums
  and permission tools as the game. Opening management does not start the table
  renderer, create table presence or broadcast a scene.
- The seven preparation tools are a personal dashboard, session planner,
  timeline/calendar, quest columns with prerequisites, document connections,
  player preview, and journal history/trash. Session plans include ordered steps,
  checklists, private notes, completion summaries and pending work. Preparation
  records remain GM-only; player previews use server-filtered documents.
- Journal history supports comparison and restoration. A restore rechecks
  visibility, prerequisites and files before committing. Missing files and stale
  versions leave existing data intact. Quest prerequisites cannot form a cycle.
- Draft session changes survive navigation to the selected session. Editors lock
  during saves, reference pickers retain a failed selection for retry, and a
  stale comparison requires a fresh comparison before restoration.
- Campaign copies, exports and snapshots include preparation, clocks, clues and
  journal history, including files retained by the trash. **Preparation** selects
  session plans, events and dashboards in a copy; history follows **Journals**.
  References and retained file identifiers are remapped to the destination.
  Portable imports assign a dashboard to the importing GM without adding source
  members or permissions. Snapshots restore each current GM's own dashboard.
  Older archives retain preparation/history they never contained when restored.

See [campaign management](../en/campaign-management.md) for limits, permissions,
archive selection and the difference between preparation and live commands.

### Progress clocks and clues

- **Clocks** works on the table and in the campaign manager, sharing campaign
  records. A clock has 2–24 segments, campaign or scene scope, GM/player audience,
  optional player progress controls and a pinned display.
- **Clues** uses staged progress with 1–24 segments. Players and streamers receive
  a finding only when discovery is complete and its audience permits revelation.
  Unfinished clues, identifiers and GM notes are filtered out on the server.
  Direct progress and configuration changes remain GM operations.
- MapBuilder's **Control clock** and **Control clue** nodes connect Smart Object
  interactions to specific GM-authored progress actions. They respect campaign
  and scene scope, require an active campaign GM and grant no general editing
  permission. Simulation describes the action; server rehearsal rolls back its
  changes and receipts.
- Clocks and clues synchronize with authorized table clients after commit.
  Campaign management refreshes through HTTP. Retries reuse the same operation
  identity; conflicting versions require a current state before retrying.

See [clocks](../en/clocks.md), [clues](../en/clues.md) and the
[MapBuilder node reference](../en/map-builder.md#control-progress-clocks).

### PDF System

- GMs can draw manual text, numeric, checkbox and multiline fields on a PDF that
  has no editable form. Native PDF fields and manual overlays use the same sheet
  value and permission contracts. Mapping is bound to the selected PDF source;
  this feature does not perform OCR or rewrite the source document.
- Double-click a field or use **F2** to configure token-bar binding and saved
  dice-roll actions. The modal offers six roll presets; formulas can use
  `@value` and `@{field-key}`. Normal dice permissions and validation apply.
- Calculated fields support bounded arithmetic and field references, with
  dependency validation and circular-reference rejection. Layout tools provide
  selection, copy/paste, alignment, distribution, snapping and undo/redo.
- Reusable mappings support JSON transfer, saved templates and batch application
  to permitted campaign actors. Export produces a flattened, filled PDF in the
  browser. Diagnostics report missing sources, invalid calculations and mapping
  mismatches instead of silently discarding them.

See the [PDF System guide](../en/pdf-system.md) for authoring, formulas, reusable
mappings, output limits and the distinction between layout definitions and values.

### MapBuilder, Universal VTT and public APIs

- **Edit map with Map Builder** in the table menu opens the current scene's linked
  project or adopts its compatible native geometry. Compatible manual scene edits
  can return to the source project; conflicting edits preserve the local draft
  and require explicit recovery. Generation and scene updates remain GM actions.
- Universal VTT import shares the native scene adapter with existing-scene
  adoption. Importing through Builder creates a linked scene and editable project;
  importing through the scene directory creates the scene, which can then be
  adopted. Walls, doors, lights, grid calibration and supported geometry receive
  native representations, with warnings for approximations.
- A finished map remains an image background: Universal VTT cannot reconstruct
  source brush strokes or separate artwork layers. Export is constrained by the
  format and does not preserve every native automation or document type.
- Public Python and JavaScript APIs expose the new clock/clue domains. PDF tools
  remain system operations through the existing generic system API. Server
  validation, resource ownership, revisions and request receipts apply to native
  UI and extensions. Native API errors retain their stable `code` and can expose
  a translated, useful `message` for display.
- The generated browser registry follows its source contract. The extension SDK
  remains **1.0.0**; its version alone does not provide newer host capabilities.
  New integrations must target a host that implements the operations they use.

See [Map Builder](../en/map-builder.md), [Universal VTT](../en/universal-vtt.md)
and the [API reference](../en/api.md).

### Pillow and compatibility

Pillow is updated from **12.3.0 to 13.0.0** in the locked dependencies and
third-party notices. Python **3.14 or newer** remains the project requirement.
Image decoding and output use the existing limits and validation. Windows checks
do not establish native Linux or macOS installer validation; follow the
[testing guide](../en/testing.md) for the corresponding platform scenarios.

Interface controls use the official Translator mechanism; English remains the
default language, with existing account/host choices preserved. Authored campaign
text retains its wording. RPG systems and their content remain independent
packages; this version does not bundle proprietary rulebooks or catalogs.

### Compatibility, migrations and data

There are **four new database migrations relative to 0.3.1**:

| App | Migration | Stored data |
| --- | --- | --- |
| `gravewright_campaigns` | `0005_preparation` | Personal dashboards, session plans, timeline events and command receipts |
| `gravewright_journals` | `0004_revision` | Journal history and retained trash metadata |
| `gravewright_table` | `0003_progress_clock` | Progress clocks and command receipts |
| `gravewright_table` | `0004_progress_clue` | Staged clues and command receipts |

Apply all pending migrations, including those from earlier versions when
upgrading an older installation. Existing PDF mapping-template migrations remain
part of the normal migration graph; no extra manual schema edits are required.

All default configuration, data, logs, tools, managed environments, caches and
update state remain inside the extracted installation: `.env`, `data/`,
`data/runner/` and `data/updates/`. Preserve local extensions and explicit operator
storage overrides. A campaign ZIP is not a full installation backup: accounts,
configuration and pending automation jobs require an installation backup.
Rollback needs compatible code and data from the same backup.

### Download and upgrade

The prepared release identifiers are **`v0.3.2`**,
**`Gravewright-0.3.2-django.zip`** and
**`Gravewright-0.3.2-django.zip.sha256`**. Their names in this document do not
assert that the tag or assets have been published. Once available, verify the
matching checksum and extract the complete ZIP into a writable folder. It
contains the Windows, Linux and macOS installers.

Version **0.3.2** is greater than **0.3.1**. Managed installations on 0.3.1 can
discover it as an upgrade once the matching release is published in the configured
repository. The earlier incorrectly numbered **3.0.1** is numerically greater
than 0.3.2, so those installations require manual installation or migration.
Preserve the historical 0.3.1 notes as the record of that earlier release.

For an installation reporting 3.0.1, back up code, configuration, database and
private media together before proceeding. Prepare 0.3.2 in a separate writable
folder and verify restoration and pending migrations using disposable copies of
that backup before switching the live installation. A version label does not
establish schema compatibility. Do not force a database downgrade, edit migration
records or run older code against a newer database. Recovery requires matching
code and data backups; see [upgrade and recovery](../en/upgrading.md).

Back up configuration, database, private media and local extensions together.
Managed installations use **Administration → Updates → Check for updates** once
the release is available. Keep the Runner open during a managed update. For a
manual upgrade, stop the Runner and other application processes, replace only
application files while preserving `.env`, `data/`, `extensions/` and explicit
storage paths, then rerun the platform installer before starting the Runner.

Source installations install the locked dependencies and migrate before restart:

```bash
uv sync --locked
uv run --locked python manage.py migrate
uv run --locked python manage.py check
```

If installing corrected files over an already installed **0.3.2**, use the manual
procedure: the updater compares versions and does not offer the same version.
See [upgrade and recovery](../en/upgrading.md) and the
[Windows](../en/windows-runner.md), [Linux](../en/linux-runner.md),
[macOS](../en/macos-runner.md) and [deployment](../en/deployment.md) guides.

## Português (Brasil)

O Gravewright 0.3.2 reúne preparação de campanha fora da mesa, relógios de
progresso compartilhados e pistas por etapas, criação ampliada de fichas PDF e
integração do MapBuilder. Estas notas descrevem o código preparado desde a
`0.3.1`. Tag publicada, download e verificações completas por plataforma são
etapas separadas da release.

### Gestor e preparação de campanha

- **Gerenciar campanha** no cartão da campanha abre a área do mestre antes de
  entrar na mesa. Mestres da campanha, inclusive comestres, usam os mesmos
  diários, missões, atores, fichas, itens, cenas, arquivos, áudio, cartas,
  compêndios e ferramentas de permissão do jogo. Abrir o gestor não inicia o
  renderizador da mesa, não cria presença na mesa nem transmite uma cena.
- As sete ferramentas de preparação são painel pessoal, planejador de sessões,
  cronologia/calendário, colunas de missões com pré-requisitos, conexões de
  documentos, prévia de jogador e histórico/lixeira de diários. Os planos têm
  etapas ordenadas, checklists, notas privadas, resumos e pendências. A
  preparação é exclusiva do mestre; prévias usam documentos filtrados no servidor.
- O histórico permite comparar e restaurar diários. A restauração revalida
  visibilidade, pré-requisitos e arquivos antes de confirmar. Arquivos ausentes
  e versões desatualizadas preservam os dados existentes. Pré-requisitos de
  missões não podem formar ciclos.
- Rascunhos de sessão sobrevivem à navegação para a sessão selecionada. Os
  editores bloqueiam durante o salvamento, seletores de referência mantêm a
  escolha após falha para permitir repetição e comparações desatualizadas
  exigem uma nova comparação antes da restauração.
- Cópias, exportações e snapshots incluem preparação, relógios, pistas e
  histórico, inclusive arquivos retidos pela lixeira. **Preparação** seleciona
  planos, eventos e painéis na cópia; o histórico acompanha **Diários**.
  Referências e identificadores de arquivos retidos são remapeados ao destino.
  Importações portáteis atribuem um painel ao mestre importador sem acrescentar
  membros ou permissões da origem. Snapshots restauram o painel de cada mestre
  atual. Restaurar arquivos antigos preserva preparação/histórico que eles nunca
  armazenaram.

Veja [gerenciamento de campanha](../pt-BR/campaign-management.md) para limites,
permissões, seleção de arquivos e diferenças entre preparação e comandos de jogo.

### Relógios de progresso e pistas

- **Relógios** funciona na mesa e no gestor com os mesmos registros. Cada relógio
  tem 2–24 segmentos, escopo de campanha ou cena, público mestre/jogadores,
  controles opcionais de progresso para jogadores e exibição fixada.
- **Pistas** usa progresso por etapas com 1–24 segmentos. Jogadores e
  transmissores recebem a descoberta somente quando ela está completa e seu
  público permite revelação. Pistas incompletas, identificadores e notas do
  mestre são filtrados no servidor. Alteração direta de progresso e configuração
  continua sendo operação do mestre.
- Os nós **Controlar relógio** e **Controlar pista** do MapBuilder conectam
  interações de Objetos Inteligentes a ações específicas criadas pelo mestre.
  Respeitam campanha e cena, exigem um mestre ativo e não concedem permissão
  geral de edição. A simulação descreve a ação; o ensaio no servidor reverte
  alterações e recibos.
- Relógios e pistas sincronizam com clientes autorizados após a confirmação.
  O gestor atualiza por HTTP. Repetições usam a mesma identidade de operação;
  conflitos de versão exigem estado atual antes de tentar novamente.

Veja [relógios](../pt-BR/clocks.md), [pistas](../pt-BR/clues.md) e a
[referência de nós do MapBuilder](../pt-BR/map-builder.md#controlar-relógios-de-progresso).

### PDF System

- Mestres podem desenhar campos manuais de texto, número, checkbox e texto
  multilinha sobre um PDF sem formulário editável. Campos nativos e sobrepostos
  usam os mesmos contratos de valores e permissões da ficha. O mapeamento fica
  vinculado à origem selecionada; o recurso não faz OCR nem reescreve o original.
- Dois cliques ou **F2** em um campo abrem configuração de vínculo com barra do
  token e rolagem salva. O modal oferece seis modelos de rolagem; fórmulas usam
  `@value` e `@{field-key}`. Validação e permissões normais de dados se aplicam.
- Campos calculados aceitam aritmética limitada e referências a campos, com
  validação de dependências e rejeição de ciclos. O editor oferece seleção,
  copiar/colar, alinhamento, distribuição, encaixe e desfazer/refazer.
- Mapeamentos reutilizáveis permitem transferência JSON, modelos salvos e
  aplicação em lote aos atores permitidos. A exportação gera um PDF preenchido
  e achatado no navegador. Diagnósticos informam origens ausentes, cálculos
  inválidos e divergências de mapeamento sem descartá-los silenciosamente.

Veja o [guia do PDF System](../pt-BR/pdf-system.md) para criação, fórmulas,
reutilização, limites da saída e diferenças entre definições do layout e valores.

### MapBuilder, Universal VTT e APIs públicas

- **Editar mapa com Map Builder** no menu da mesa abre o projeto vinculado à cena
  atual ou adota sua geometria nativa compatível. Edições manuais compatíveis
  retornam ao projeto; conflitos preservam o rascunho local e exigem recuperação
  explícita. Gerar e atualizar cenas continuam sendo ações do mestre.
- A importação Universal VTT compartilha o adaptador nativo com a adoção de cenas.
  Importar pelo Builder cria cena e projeto editável vinculados; importar pelo
  diretório cria a cena, que pode ser adotada depois. Paredes, portas, luzes,
  calibração da grade e geometria compatível recebem representações nativas,
  com avisos quando há aproximações.
- Um mapa pronto continua sendo uma imagem de fundo: Universal VTT não reconstrói
  pinceladas nem camadas de arte originais. A exportação respeita os limites do
  formato e não conserva toda automação ou tipo de documento nativo.
- As APIs públicas Python e JavaScript expõem relógios e pistas. Ferramentas PDF
  permanecem operações do sistema pela API genérica existente. Validação,
  propriedade de recursos, revisões e recibos se aplicam à interface e às
  extensões. Erros nativos preservam `code` estável e podem fornecer `message`
  útil e traduzida para exibição.
- O registro gerado do navegador acompanha o contrato-fonte. O SDK permanece
  **1.0.0**; sua versão isolada não fornece capacidades de hosts mais recentes.
  Integrações devem apontar para um host que implemente as operações usadas.

Veja [Map Builder](../pt-BR/map-builder.md), [Universal VTT](../pt-BR/universal-vtt.md)
e a [referência da API](../pt-BR/api.md).

### Pillow e compatibilidade

O Pillow passa de **12.3.0 para 13.0.0** nas dependências fixadas e nos avisos
de terceiros. O requisito continua sendo **Python 3.14 ou superior**. Decodificação
e saída de imagens mantêm os limites e a validação existentes. Verificações no
Windows não comprovam validação nativa dos instaladores Linux ou macOS; o
[guia de testes](../pt-BR/testing.md) descreve os cenários de cada plataforma.

Controles da interface usam o Translator oficial; inglês continua sendo o idioma
padrão, com escolhas existentes de conta/host preservadas. Textos de campanha
mantêm sua redação. Sistemas e seus conteúdos continuam em pacotes independentes;
esta versão não inclui livros de regras nem catálogos proprietários.

### Download e atualização

Os identificadores preparados são **`v0.3.2`**,
**`Gravewright-0.3.2-django.zip`** e
**`Gravewright-0.3.2-django.zip.sha256`**. Citá-los neste documento não afirma que
a tag ou os arquivos já foram publicados. Quando disponíveis, confira o checksum

edite registros de migrações nem execute código antigo contra um banco mais novo.
A recuperação exige backups compatíveis de código e dados; veja
[atualização e recuperação](../pt-BR/upgrading.md).

Faça backup conjunto de configuração, banco, mídias privadas e extensões locais.

atualizações** quando a release estiver disponível. Mantenha o Runner aberto na

`data/`, `extensions/` e caminhos explícitos e execute novamente o instalador
da plataforma antes de iniciar o Runner.

Instalações pelo código-fonte instalam dependências fixadas e migram antes de reiniciar:

```bash

```

Se substituir arquivos de uma **0.3.2** já instalada por uma correção da mesma
versão, use o procedimento manual: o atualizador compara versões e não oferece
a mesma versão. Veja [atualização e recuperação](../pt-BR/upgrading.md) e os
guias de [Windows](../pt-BR/windows-runner.md), [Linux](../pt-BR/linux-runner.md),
[macOS](../pt-BR/macos-runner.md) e [implantação](../pt-BR/deployment.md).
