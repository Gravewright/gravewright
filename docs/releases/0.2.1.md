# Gravewright 0.2.1 — Alpha

Gravewright 0.2.1 expands the host APIs for independent systems and improves the
native item, compendium and card workflows. The project remains an Alpha preview.
Game rules, document types and licensed content stay with their system providers;
the VTT supplies shared storage, permissions, windows and encounter management.

The release package was refreshed on **13 October 2026** to add Linux/macOS
installation and POSIX Runner recovery. Version `0.2.1`, Alpha stage, update
channel `stable` and the download asset names remain unchanged.

## Changes

- **System-defined combat.** The optional `system.combat` manifest declaration
  configures initiative formulas, manual input and roll controls. Trusted server
  providers can prepare initiative and advance their own effects. The host scopes
  updates to encounter participants and keeps independent token snapshots separate
  from their source actors. A new encounter identifier distinguishes successive
  combats in the same scene.
- **Compendiums supplied by systems.** `content.compendiums` declares validated
  collections inside signed packages. Tables expose the exact activated system
  release, respecting current read grants and package integrity. A compact index
  and authorized batch reads load documents on demand, without copying every entry
  into the table library. Shared content caching preserves permission checks.
- **Shared module modals.** `api.ui.openModal()` provides nested windows, focus
  handling, Escape and temporary suspension for map interactions. Actor sheets,
  item sheets and modals can await pending saves through
  `gravewright:sheet-flush`; a failed save keeps the window open.
- **Provider-owned documents.** Actor and item types can declare translated labels
  and icons. Core creation, validation, sheet mounting and token snapshots use
  provider metadata. The bundled PDF System retains its existing campaign IDs and
  data through the same provider boundary.
- **Items and cards.** The item directory gains compact rows, search, folders and
  a context menu that opens the full system editor. The card hand and its preview,
  draw, removal and permission flows use the shared modal component, including
  restoration after dragging a card onto the map.
- **Translation and dice presentation.** Private Translator catalogs can supply
  document-type labels; catalog registration and disposal notify subscribed UI.
  Named parameters, number formatting and locale fallback remain available through
  `context.i18n` / `api.i18n`. Native dice presets describe their formulas without
  assuming a particular game's rules.
- **Windows Marketplace installation.** The installer verifies the official
  public-key file against an immutable repository revision and matching SHA-256,
  retaining both approved signing keys. Existing Marketplace configuration is
  preserved.
- **Canonical storage paths.** Installed packages and startup recovery accept
  equivalent storage roots, including macOS `/var` aliases and Windows short
  paths. Package integrity checks continue to reject internal symbolic links
  and changed files.

See the [module guide](../en/modules.md) for the manifest, provider, compendium,
modal and translation contracts, and the [API guide](../en/api.md) for public
Python and browser entry points.

## Compatibility and limits

**0.2.1 is the first VTT release supporting the new `system.combat`,
`content.compendiums`, combat-provider and module-modal saving contracts.** Update
the host before installing systems that require them. The browser SDK remains
**1.0.0**: these additions do not change its major contract, and the SDK version
alone cannot identify these capabilities in an older host. VTT, SDK and extension
versions are independent.

Browser packages declare data and UI; executable server rules require a separately
installed, trusted Django provider. A system with `requiresProvider: true` reports
a missing provider instead of silently running incomplete combat rules. Without
an effect provider, the core leaves the system's sheet effects untouched.

Compendium reads still require table membership and read permission. Player read
access does not grant permission to import into the library. Package selection,
revocation and integrity are rechecked when content is read; a cache never grants
access. Type labels and rules data come from the provider, and user-authored text
is preserved.

System modules and their content remain separate downloads. The **5e SRD system
0.1.0 is not included** in the VTT archive. Its rules, translations and content are
versioned and distributed independently.

## Package refresh — 13 October 2026

- **Linux installer.** `Install Linux.sh` detects `/etc/os-release` `ID` and
  `ID_LIKE` for Debian, Fedora/RHEL, SUSE, Arch and Alpine families. It supports
  x64 and ARM64, distinguishes glibc/musl and prepares verified private tools.
  The official Node.js fallback requires glibc 2.28+ and kernel 4.18+.
  Alpine/musl requires compatible Node.js 22/24 and npm 10+ already available;
  recognizing that family does not imply every Alpine combination was tested.
- **macOS installer.** `Install macOS.command` supports macOS 13.5+ on Intel
  x64 and Apple Silicon ARM64. It uses the native platform's tools and archives,
  without requiring Homebrew or permanent shell/PATH changes.
- **Separate installation and startup.** Both installers reuse compatible tools
  or prepare private uv, CPython 3.14 and Node.js/npm, install locked dependencies,
  build/reuse the frontend, save configuration and generate `Gravewright Runner.sh`
  or `Gravewright Runner.command`. Startup uses the prepared environment and
  does not repeat installation questions or dependency downloads. Shell files
  retain executable permissions in the release archive.
- **Local configuration and recovery.** Configuration remains in project `.env`;
  database/media follow its configured paths. Runner state/tools use private
  per-user directories. Generated immutable launcher copies survive in-place
  replacements; interrupted update transactions recover on the next start.
  POSIX `SIGHUP` uses orderly shutdown and supervisor cleanup.

### Reinstalling a host already on 0.2.1

The automatic updater compares numeric versions and will not offer the refreshed
0.2.1 package to a host already on 0.2.1. Download **Gravewright-0.2.1-django.zip**
again together with its matching **.sha256** file. The earlier archive's checksum
does not validate the refreshed bytes.

1. Stop the Runner and back up project `.env`, the configured database, private
   media/installed packages and Runner state, including update recovery data.
2. Extract the complete refreshed archive and replace application files in the
   existing installation folder, preserving configuration and data. Keep a
   matching copy of the earlier code and backup for rollback.
3. Run `Install Windows.bat`, `bash "./Install Linux.sh"` or
   `Install macOS.command`, according to the host. Use the regenerated Runner.
   If moving the project, preserve storage paths and prepare the new location
   with the installer. Do not copy only an entrypoint without its support scripts.

Hosts upgrading from an older numeric version can still use Administration →
Updates. The same-version procedure above is specific to hosts already on 0.2.1.
See the [Windows](../en/windows-runner.md), [Linux](../en/linux-runner.md) and
[macOS](../en/macos-runner.md) guides for paths, flags and platform limits.

## Download and upgrade

Use **Gravewright-0.2.1-django.zip** with its matching **.sha256** file.
The ZIP contains the application and built frontend assets;
Translator and third-party systems remain separate packages.

Before upgrading, stop the application and make a consistent backup of the
configured database, private media, installed packages and configuration,
including the persistent secret and trust keys. Campaign exports are not a full
instance backup. Keep the matching old source and backup together for rollback;
do not run old code over a newly migrated database.

For managed installations, use **Administration → Updates**.
The managed update prepares dependencies, runs migrations and restarts the host.
For an operator-managed source checkout, update the files, run
`uv sync --locked` and `uv run --locked python manage.py migrate`, prepare the
deployment's static assets and restart the server. Run migrations when upgrading
from 0.2.0 too: provider-backed defaults are added without converting existing
system IDs or sheet content.

On Windows, extract the complete project and run **Install Windows.bat** to
prepare a new installation. After manually moving or replacing an existing
project, run the installer in its new location to regenerate **Gravewright
Runner.bat** and its shortcut. Preserve the project's `.env` and its configured
database/media paths; Runner tools and caches under `%LOCALAPPDATA%\Gravewright`
are separate from those settings.

See [deployment and backups](../en/deployment.md) and the
[Windows](../en/windows-runner.md), [Linux](../en/linux-runner.md) and
[macOS](../en/macos-runner.md) Runner guides. The numeric identifier `0.2.1`
follows the existing `stable` update-channel convention; the project's development
stage remains Alpha.

  tests were skipped on Windows. This includes Marketplace integrity and
  canonical storage-path regressions.
- All 110 JavaScript tests passed, including module lifecycle, modal APIs,
  translation, dice presets, map models and realtime replay.
- Django system checks, migration consistency, locked dependency metadata,
  generated frontend contract and effective native translation catalogs passed.
- Playwright exercised an extracted release archive with Translator 0.1.2 and
  PDF sheets in English, Brazilian Portuguese and Spanish, with no browser errors.
  Nested modal focus, pending saves, rejected saves and forced cleanup also passed.
- The native Windows installer passed tool downloads, offline reuse, Unicode
  paths, interactive Portuguese settings, shortcut and generated-launcher checks.
  The real Runner browser scenario passed setup, HTTP/WebSocket permissions,
  shutdown and persistence of sessions, chat, media and configuration on restart.
- Managed updates passed invalid-checksum rejection, in-place replacement,
  preservation of installed apps and data, recovery from migration/startup
  failures, optional `.old` retention and explicit rollback of code and data.
- A separate 5e 0.1.0 package and its trusted companion were installed into an
  extracted VTT archive through the package host and managed activation. Sheets,
  compendium drops, autosave, translation and provider-backed initiative passed.

## Português (Brasil)

O **Gravewright 0.2.1 Alpha** amplia as APIs para sistemas independentes e melhora
os fluxos de itens, compêndios e cartas. As regras, os tipos de documento e o
conteúdo licenciado pertencem aos provedores de cada sistema. O VTT oferece
armazenamento, permissões, janelas e gerenciamento dos encontros.

O pacote da release foi atualizado em **13 de outubro de 2026** com instalação
Linux/macOS e recuperação do Runner POSIX. Versão `0.2.1`, estágio Alpha, canal
de atualização `stable` e nomes dos arquivos de download permanecem iguais.

- **Combate definido pelo sistema.** A declaração opcional `system.combat`
  configura fórmulas de iniciativa, entrada manual e controles de rolagem.
  Provedores de servidor podem preparar a iniciativa e avançar seus próprios
  efeitos. As atualizações ficam limitadas aos participantes do encontro, e tokens
  independentes usam seus próprios dados. Um identificador de encontro diferencia
  combates iniciados na mesma cena.
- **Compêndios dos sistemas.** `content.compendiums` declara coleções validadas
  nos pacotes assinados. A mesa usa a versão exata do sistema ativado, com controle
  de leitura e integridade. O índice compacto e a leitura autorizada em lote
  carregam os documentos sob demanda, sem copiar toda a coleção para a biblioteca.
  O cache compartilhado preserva as verificações de acesso.
- **Modais compartilhadas.** `api.ui.openModal()` oferece janelas aninhadas,
  controle de foco, Escape e suspensão temporária para interagir com o mapa.
  Fichas de ator, fichas de item e modais aguardam gravações pendentes por
  `gravewright:sheet-flush`; uma falha ao salvar mantém a janela aberta.
- **Documentos definidos pelo provedor.** Tipos de ator e item podem declarar
  rótulos traduzidos e ícones. Criação, validação, montagem da ficha e dados dos
  tokens usam metadados do provedor. O PDF System integrado mantém os IDs e dados
  das campanhas existentes por essa mesma interface.
- **Itens e cartas.** O diretório de itens recebe linhas compactas, busca, pastas
  e menu de contexto que abre o editor completo do sistema. A mão de cartas e os
  fluxos de prévia, compra, remoção e permissões usam a modal compartilhada,
  inclusive ao retornar depois de arrastar uma carta para o mapa.
- **Traduções e dados.** Catálogos privados do Translator fornecem os rótulos
  dos tipos de documento. Registro e remoção de catálogos atualizam a interface
  inscrita nesses eventos. Parâmetros, números e fallback de idioma continuam
  disponíveis em `context.i18n` / `api.i18n`. Os presets de dados descrevem suas
  fórmulas sem assumir regras de um jogo específico.
- **Marketplace no Windows.** O instalador verifica o arquivo oficial de chaves
  públicas com uma revisão imutável do repositório e SHA-256 correspondente,
  preservando as duas chaves de assinatura aprovadas. A configuração de
  Marketplace existente é mantida.
- **Caminhos de armazenamento.** Pacotes instalados e recuperação na
  inicialização aceitam raízes equivalentes, incluindo aliases de `/var` no
  macOS e nomes curtos no Windows. A verificação de integridade dos pacotes
  continua rejeitando links simbólicos internos e arquivos alterados.

Consulte os [contratos de módulos](../pt-BR/modules.md) e a
[referência da API](../pt-BR/api.md).

**A 0.2.1 é a primeira versão do VTT com os novos contratos `system.combat`,
`content.compendiums`, provedores de combate e salvamento das modais de módulos.**
Atualize o host antes de instalar sistemas que dependam deles. O SDK de navegador
permanece **1.0.0**, com adições compatíveis; sua versão, isoladamente, não comprova
essas capacidades em hosts antigos. VTT, SDK e extensões têm versões independentes.

Pacotes de navegador declaram dados e interface. Regras executáveis de servidor
exigem um provedor Django confiável, instalado separadamente. Com
`requiresProvider: true`, a ausência desse provedor gera um erro explícito. Sem um
provedor de efeitos, o núcleo preserva os efeitos da ficha sem interpretá-los.

Ler um compêndio exige participação na mesa e permissão de leitura; isso não
autoriza um jogador a importar documentos para a biblioteca. Versão ativada,
revogação e integridade continuam verificadas em cada leitura. O conteúdo criado
pelos usuários mantém seu texto original. O **sistema 5e SRD 0.1.0 não está
incluído** no arquivo do VTT; sistemas, traduções e conteúdo são distribuídos
separadamente.

### Reempacotamento — 13 de outubro de 2026

- **Instalador Linux.** `Install Linux.sh` detecta `ID` e `ID_LIKE` de
  `/etc/os-release` para as famílias Debian, Fedora/RHEL, SUSE, Arch e Alpine.
  Suporta x64/ARM64, distingue glibc/musl e prepara ferramentas privadas
  verificadas. O Node.js oficial alternativo exige glibc 2.28+ e kernel 4.18+.
  Alpine/musl precisa de Node.js 22/24 e npm 10+ compatíveis já disponíveis;
  reconhecer a família não significa que toda combinação Alpine foi testada.
- **Instalador macOS.** `Install macOS.command` atende ao macOS 13.5+ em Intel
  x64 e Apple Silicon ARM64, usando ferramentas e pacotes da plataforma nativa,
  sem exigir Homebrew ou mudanças permanentes de shell/PATH.
- **Instalar e iniciar são etapas separadas.** Os instaladores reaproveitam
  ferramentas compatíveis ou preparam uv, CPython 3.14 e Node.js/npm privados,
  instalam dependências fixadas, compilam/reutilizam o frontend, salvam a
  configuração e geram `Gravewright Runner.sh` ou `Gravewright Runner.command`.
  O Runner usa o ambiente pronto, sem repetir perguntas ou baixar dependências.
  O pacote preserva as permissões de execução dos scripts.
- **Configuração e recuperação.** O `.env` permanece no projeto; banco e mídia
  seguem seus caminhos configurados. Ferramentas e estado do Runner ficam em
  pastas privadas por usuário. Cópias imutáveis do launcher sobrevivem à troca
  dos arquivos; transações de atualização interrompidas são recuperadas ao
  iniciar novamente. `SIGHUP` usa encerramento ordenado e limpeza do supervisor.

#### Reinstalar um host que já usa 0.2.1

O atualizador compara versões numéricas e não oferece o pacote 0.2.1 atualizado
a um host que já está na 0.2.1. Baixe novamente **Gravewright-0.2.1-django.zip**
e seu **.sha256** correspondente. O checksum do pacote anterior não valida os
novos bytes.

1. Pare o Runner e faça backup de `.env`, banco configurado, mídias privadas,
   pacotes instalados e estado do Runner, incluindo a recuperação de atualizações.
2. Extraia o pacote atualizado completo e substitua os arquivos da aplicação na
   pasta existente, preservando configuração e dados. Guarde o código anterior
   com seu backup correspondente para rollback.
3. Execute `Install Windows.bat`, `bash "./Install Linux.sh"` ou
   `Install macOS.command`, conforme a plataforma, e use o Runner regenerado.
   Ao mover o projeto, preserve os caminhos dos dados e prepare a nova pasta
   com o instalador. Não copie somente o script de entrada sem os de apoio.

Hosts em uma versão numérica anterior ainda podem usar Administração →
Atualizações. O procedimento manual acima é específico para hosts já na 0.2.1.
Consulte os guias [Windows](../pt-BR/windows-runner.md),
[Linux](../pt-BR/linux-runner.md) e [macOS](../pt-BR/macos-runner.md).
