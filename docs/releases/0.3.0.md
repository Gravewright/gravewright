# Gravewright 0.3.0 — Alpha

## Changes

Gravewright 0.3.0 adds map authoring and visual automation, with the changes
below since `v0.2.3`.

The main addition is **Map Builder**: a persistent map editor with native scene
generation, visual **Smart Object** automation and **Universal VTT** interchange.
The update also improves tabletop rendering, map uploads, interface density and
frontend organization.

### Map Builder and scene authoring

- **Independent GM workspace.** Open **New scene → Map Builder** to prepare a
  map without changing the current scene or the players' broadcast. Projects
  belong to their campaign and can be reopened from the project list or a linked
  scene's **Edit with MapBuilder** action.
- **Tiles and Painting.** Paint floors with textures, solid colors or asset
  families; draw walls and independent doors; place objects, lights, particles,
  shaders and presence regions. Grid snapping, fractional placement, shapes,
  soft terrain brushes, opacity, holes and layer-local floor erasure share the
  same project. Material families preserve each painted object's chosen image.
- **Layers and editing tools.** Named layers support ordering, visibility,
  locking, isolation, duplication and merge operations. Selection, multiple
  selection, duplication, transforms, wall nodes and joins, object names,
  Undo/Redo and Preview follow the same geometry and ownership rules. Hidden
  layers organize editing; generated scenes include every project layer.
- **Finished-map backgrounds.** Import a PNG, JPEG, WebP or TIFF image, or choose
  one already in the campaign, and set its dimensions in cells. It fills the map
  once beneath the authored content. Replacing the background preserves objects
  and rejects dimensions that would put them outside the map.
- **Automatic saving and recovery.** Project and valid Smart Object edits save
  automatically. Pending writes retain their logical request identity when the
  response is uncertain. Conflicts preserve the local draft and offer explicit
  reload or copy recovery. Retry controls resume interrupted project saves;
  returning to the game waits for pending edits. Saving a project does not
  execute its behavior or update a generated scene.
- **Generate and update explicitly.** Generation creates a new GM-only native
  scene. **Update scene** refreshes the linked scene in place, preserving its
  identity, manually placed content and compatible live state. Project and
  scene revisions prevent silent overwrites of concurrent or manual changes.
  Activating the scene for players remains a separate operation.
- **Empty Objects and dynamic surfaces.** Image-free Empty Objects provide
  private controllers on the GM layer. Floors and walls can become dynamic
  surfaces whose appearance or visibility changes during play while their
  collision remains independently controlled. Ordinary artwork also supports
  moving between public and private image layers.
- **Door pivots.** Doors can rotate around their start, center or end. Opening
  a door with an explicit pivot rotates its image by 90°; closing restores it.
  Inherited artwork without an explicit pivot remains hidden while open, and
  a Blueprint's explicit hidden appearance stays hidden.

See [Map Builder](../en/map-builder.md) for the authoring workflow, limits and
the policy for updating linked scenes.

### Smart Objects and Blueprint automation

- **Visual event graphs.** Doors, levers, composed torches, Empty Objects and
  regions can own events, conditions and actions. Execution and typed value
  wires connect element instances, resource references and ordered groups.
  Events start sequences; explicit actions change state, sprites, lights,
  audio, barriers or other supported properties.
- **Conditions, data and control flow.** State checks, All/Any, typed variables,
  comparisons, named signals, Switch, weighted Random and Sequence support
  cross-element behavior. Counter, Once and event-driven Cooldown retain their
  progress. Event Context supplies authoritative token, actor and presence
  information instead of trusting a browser-selected identity.
- **Area events and composed mechanisms.** Named regions, pressure plates and
  object areas react to accepted token entry and exit. Filters select eligible
  tokens or actors. A torch keeps its mechanism state independent from its flame
  and owns its linked native light/effect components. State changes do not
  implicitly invoke another object's interaction graph.
- **Durable Delay and Timer.** Server-side continuations and named one-shot
  timers survive disconnection and server restart. The ASGI worker resumes
  eligible work with current access checks and the original actor's authority
  ceiling. Pausing scene automation retains pending jobs until resumed.
- **World and presentation actions.** Supported targets can move, rotate,
  change artwork or interaction settings, and control native resources.
  Messages, journal handouts and camera focus use authorized audiences; camera
  focus requires the recipient's opt-in. Same-scene Teleport moves the
  authenticated triggering token to a validated destination region without
  animating the skipped path or changing the campaign's broadcast.
- **Reuse and scene overview.** Campaign templates copy behavior with explicit
  typed resource bindings. The scene network opens the same element-owned
  graphs, and the GM's Automation window exposes compatible native controls,
  pending work, variables and node memory.
- **Rehearsal and diagnostics.** **Test behavior** runs the real server engine
  against a Builder draft or live scene and rolls back its effects. Reports
  show settled state, affected elements and token context in readable terms,
  with raw values under technical details. Local **Simulate** remains a
  graph-only preview. The private Automation log keeps the last 50 runs per
  scene. Rehearsal does not advance timers or deliver live presentation/audio.
  It uses the GM's permissions; check actual player permissions separately.

Execution uses bounded chains, server permissions, transactions and retry
receipts. Players and streamers receive authorized current presentation rather
than private graph definitions or GM-only artwork. Runtime updates reuse
authorized textures and send committed scene changes before dependent refreshes.

Current limits remain explicit: named signals have no custom payload; templates
are snapshots; arbitrary property searches, visual node groups/comments,
reroutes and bypass are unavailable. Cross-scene teleport and group travel are
future work. See [Smart Objects](../en/map-builder.md#door-smart-objects) and
[the implementation status](../en/smart-objects-direction.md).

### Universal VTT import and export

- Import `.uvtt`, `.dd2vtt` or `.df2vtt` files using **Universal VTT 0.2** with
  an embedded PNG or WebP image. Resolution, grid origin, wall lines, portal
  bounds and lights become a new native scene, initially visible only to the GM.
  Fractional origins retain grid alignment, and collinear wall spans are cut at
  door openings.
- Export the current native scene with its tiled background, public image
  placements, active dynamic materials, wall/door geometry and enabled lights.
  Open door artwork respects its pivot, and fitted sprite/state images retain
  their displayed size even outside the ordinary image editor's scale range.
- The importer validates file structure, image dimensions, numbers, ownership
  and work limits. Retrying the same import returns its existing scene; failed
  imports remove newly stored tiles. Export is read-only and excludes GM-only
  artwork.
- Warnings identify format differences: portal/window interpretation, ambient
  color, baked lighting, shadow settings and clamped light values. Review them
  before broadcasting an imported map or downloading an export.

Universal VTT creates an interchange copy. It does not recover a Map Builder
project from a flattened map, and it does not preserve graphs, timers, tokens,
cards, permissions, fog, drawings or audio. Individual images and dynamic
materials become background pixels; locks, secret presentation, height ranges
and separate barrier channels are not retained. Keep the original campaign and
project when those features matter. See [Universal VTT](../en/universal-vtt.md).

### Tabletop rendering, uploads and interface

- Lighting and vision reuse bounded wall indices and occlusion results. Larger
  visibility jobs use a disposable same-origin module worker with synchronous
  fallback. Animated lights reuse immutable textures; shader light maps use the
  GPU, and particle sampling has bounded CPU work. Resources are released when
  their scene or viewer role changes. These changes do not establish a
  universal frame-rate improvement on physical GPUs.
- Scene image uploads share a bounded Pillow/libvips tiling pipeline with
  orientation, dimension, pixel and tile-count validation. Both engines produce
  lossless WebP tiles. The optional `vips` extra supports libvips; default
  installers keep Pillow available. `GRAVEWRIGHT_MAP_TILER=auto` uses libvips
  when installed and otherwise falls back to Pillow. Large maps still require
  appropriate memory, temporary disk capacity and configured limits.
- Native windows, directories, administration and the bundled PDF System use
  more compact spacing and consistent design tokens while keeping host
  interface text at least 12px. Authored document text keeps its own sizes.
  Items, types and compendium entries use locale-aware sorting; compendium
  creation, previews and import controls retain their permission checks.
  Actor template upload controls sit beneath the primary actions and above
  search.
- The Builder workspace separates canvas rendering, properties, layers,
  persistence, imports and library controls. Native tools, preview and editors
  use named ES modules, share Pixi and retain lazy loading. Public entry URLs,
  worker compatibility and Runner output verification remain intact; unused
  generated chunks are removed. More module requests can add overhead to a
  cold individual import, so this refactor is not a blanket startup-speed claim.
- Reliability fixes cover rejected versus uncertain autosave attempts, sound
  deletion in dynamic generation recipes, very small or large decoration fits,
  Blueprint door rotation and current-scene signal delivery. Updater recovery
  backs up stale idle active-release metadata locally and refuses to rebind it
  while pending update state exists.

See [rendering and frontend organization](../en/frontend.md),
[map tiling configuration](../en/configuration.md#map-tiling-and-large-images)
and [deployment](../en/deployment.md) for operating requirements.

### Compatibility, migrations and data

The SDK remains **1.0.0**, with no change to its public contract versions in this
update. Host feature availability still depends on the VTT version; SDK
compatibility does not add Map Builder or Blueprint capabilities to older hosts.
Independent RPG systems continue to own their sheets, rules, catalogs and assets.
The new libvips dependency group is optional; the mandatory runtime dependency
list is unchanged.

**This update adds six database migrations.** Maps migrations `0008` through `0013`
create project storage and generation history, automation diagnostics and
durable jobs, named timer constraints, campaign Blueprint templates and
scene-owned generated artwork. Apply the normal migration workflow before
starting the updated server. Do not run older code against the migrated database.

Before upgrading to 0.3.0, stop application writes and back up the matching
configuration, configured database, private media, content collections and local
extensions. Preserve `.env`, `data/` and explicit operator storage paths during
file replacement. Rollback needs matching code and data backups, not merely the
previous executable files. Default runtime storage continues to stay inside each
extracted installation.

Pending Delay/Timer jobs live in the instance database and resume when the ASGI
worker is available, including overdue work after restart. Campaign exports,
snapshots and copies exclude those pending jobs; automation logs are also
excluded from campaign archives. They are not a substitute for a consistent
full-instance backup. When inspecting a restored copy, disable its automation
worker with `GRAVEWRIGHT_AUTOMATION_WORKER_ENABLED=false` until it is ready to
execute pending work.

For projects from interim development builds, the current executable Blueprint
format is version 2. Loading older containers discards retired `onChange` and
state-specific event graphs while retaining supported elements and sequences.
Keep a backup and review those behaviors before adopting the newer format.

The [testing guide](../en/testing.md) describes isolated suites and native
installation and upgrade scenarios for contributors.

### Download and upgrade

Use **`Gravewright-0.3.0-django.zip`** with its matching checksum file,
**`Gravewright-0.3.0-django.zip.sha256`**, from release tag **`v0.3.0`**.
The complete ZIP contains the Windows, Linux and macOS installers.

Installations on **0.2.3** can upgrade to **0.3.0** through
**Administration → Updates → Check for updates**. Back up configuration and
data together before starting the update, as described above.

For a manual upgrade, stop the Runner, replace application files while
preserving `.env`, `data/`, local extensions and explicit operator storage
paths, then rerun the platform installer. The installer prepares the locked
dependencies and applies the normal migration workflow. Source installations
must install the locked dependencies and run migrations before starting the
updated server. A rollback requires the matching code and data backups.

The version identifier is `0.3.0`; the project continues in the **Alpha**
development stage. English remains the default interface language, and saved
host and account language preferences are preserved.

## Português (Brasil)

O Gravewright 0.3.0 acrescenta criação de mapas e automação visual, com as
mudanças abaixo desde `v0.2.3`.

A principal novidade é o **Map Builder**: um editor persistente de mapas com
geração de cenas nativas, automação visual por **Smart Objects** e intercâmbio
**Universal VTT**. A atualização também melhora renderização da mesa, upload de
mapas, densidade da interface e organização do frontend.

### Map Builder e criação de cenas

- **Área independente do mestre.** Abra **Nova cena → Map Builder** para preparar
  um mapa sem mudar a cena atual nem a transmissão dos jogadores. Os projetos
  pertencem à campanha e podem ser reabertos pela lista de projetos ou pela
  ação **Editar com MapBuilder** da cena vinculada.
- **Tiles e Pintura.** Pinte pisos com texturas, cores sólidas ou famílias de
  recursos; desenhe paredes e portas independentes; coloque objetos, luzes,
  partículas, shaders e regiões de presença. Encaixe na grade, posições
  fracionárias, formas, pincéis suaves de terreno, opacidade, recortes e remoção
  de piso por camada compartilham o mesmo projeto. As famílias preservam a
  imagem escolhida para cada elemento pintado.
- **Camadas e ferramentas de edição.** Camadas nomeadas oferecem ordenação,
  visibilidade, bloqueio, isolamento, duplicação e mesclagem. Seleção, seleção
  múltipla, duplicação, transformações, nós e junções de paredes, nomes de
  elementos, Desfazer/Refazer e Prévia seguem as mesmas regras de geometria e
  propriedade. Camadas ocultas organizam a edição; a cena gerada inclui todas
  as camadas do projeto.
- **Mapas prontos como fundo.** Importe PNG, JPEG, WebP ou TIFF, ou escolha uma
  imagem já existente na campanha, e informe suas dimensões em células. Ela
  preenche o mapa uma única vez sob o conteúdo criado. Trocar o fundo preserva
  os objetos e rejeita dimensões que os deixariam fora do mapa.
- **Salvamento automático e recuperação.** Alterações do projeto e edições
  válidas de Smart Objects são salvas automaticamente. Envios cuja resposta é
  incerta preservam a identidade da operação nas tentativas seguintes. Conflitos
  mantêm o rascunho local e oferecem recuperação explícita por recarga ou cópia.
  Os controles de tentar novamente retomam salvamentos interrompidos; voltar ao
  jogo aguarda as edições pendentes. Salvar o projeto não executa comportamentos
  nem atualiza uma cena gerada.
- **Geração e atualização explícitas.** A geração cria uma nova cena nativa
  exclusiva do mestre. **Atualizar cena** modifica a cena vinculada no lugar,
  preservando identidade, conteúdo colocado manualmente e estado de jogo
  compatível. Revisões do projeto e da cena evitam sobrescrever silenciosamente
  alterações manuais ou concorrentes. Ativar a cena para jogadores continua
  sendo uma operação separada.
- **Objetos vazios e superfícies dinâmicas.** Empty Objects sem imagem funcionam
  como controladores privados na camada GM. Pisos e paredes podem se tornar
  superfícies dinâmicas cuja aparência ou visibilidade muda durante o jogo,
  mantendo o controle independente da colisão. Imagens comuns também podem
  passar entre as camadas de imagem pública e privada.
- **Pivôs das portas.** Portas podem girar pelo início, centro ou fim. Abrir uma
  porta com pivô explícito gira sua imagem em 90°; fechar restaura a posição.
  A imagem herdada sem pivô explícito continua oculta enquanto a porta está
  aberta, e a aparência explicitamente oculta de um Blueprint continua oculta.

Veja [Map Builder](../pt-BR/map-builder.md) para o fluxo de criação, limites e
política de atualização das cenas vinculadas.

### Smart Objects e automação Blueprint

- **Grafos visuais de eventos.** Portas, alavancas, tochas compostas, objetos
  vazios e regiões podem ter eventos, condições e ações. Conexões de execução e
  valores tipados ligam instâncias, referências a recursos e grupos ordenados.
  Eventos iniciam sequências; ações explícitas alteram estado, sprites, luzes,
  áudio, barreiras e outras propriedades compatíveis.
- **Condições, dados e fluxo.** Verificações de estado, Todas as condições,
  Qualquer condição, variáveis tipadas, comparações, sinais nomeados, Escolher
  caminho, Aleatório com pesos e Sequência permitem comportamentos entre
  elementos. Contador, Uma vez e Recarga acionada por eventos preservam seu
  progresso. O contexto do evento fornece informações
  autoritativas de token, ator e presença, sem confiar numa identidade escolhida
  pelo navegador.
- **Eventos de área e mecanismos compostos.** Regiões nomeadas, placas de
  pressão e áreas de objetos respondem à entrada e saída aceitas dos tokens.
  Filtros selecionam tokens ou atores elegíveis. Uma tocha mantém o estado do
  mecanismo independente da chama e controla seus componentes nativos de luz e
  efeitos. Mudar um estado não chama implicitamente a interação de outro objeto.
- **Delay e Timer persistentes.** Continuações no servidor e temporizadores
  nomeados de execução única sobrevivem à desconexão e ao reinício. O worker
  ASGI retoma trabalho elegível com verificações atuais de acesso e o limite de
  autoridade do participante original. Pausar a automação da cena preserva os
  trabalhos pendentes até a retomada.
- **Ações no mundo e apresentação.** Alvos compatíveis podem mover, girar,
  trocar imagens ou configurações de interação e controlar recursos nativos.
  Mensagens, documentos de diário e foco da câmera usam públicos autorizados;
  o foco exige consentimento nas preferências do destinatário. Teleport na mesma
  cena move o token autenticado do evento para uma região de destino validada,
  sem animar o caminho pulado nem mudar a transmissão da campanha.
- **Reutilização e visão da cena.** Modelos da campanha copiam comportamentos
  com vínculos explícitos e tipados de recursos. A rede da cena abre os mesmos
  grafos dos elementos, e a janela de Automação do mestre expõe controles nativos
  compatíveis, trabalhos pendentes, variáveis e memória dos nós.
- **Ensaio e diagnóstico.** **Testar comportamento** usa o mecanismo real do
  servidor num rascunho do Builder ou cena existente e reverte seus efeitos.
  Os relatórios mostram o estado final, elementos afetados e contexto do token
  de forma legível, com valores brutos nos detalhes técnicos. **Simular** mantém
  a prévia local de um grafo. O log privado de Automação guarda as últimas 50
  execuções por cena. O ensaio não avança temporizadores nem entrega áudio ou
  apresentações ao vivo.
  Ele usa as permissões do mestre; confira separadamente o acesso dos jogadores.

A execução usa cadeias limitadas, permissões do servidor, transações e recibos
para novas tentativas da mesma operação. Jogadores e streamers recebem a
apresentação atual autorizada, preservando a privacidade dos grafos e das imagens
exclusivas do mestre. Atualizações em jogo reutilizam texturas autorizadas e
enviam alterações confirmadas da cena antes das atualizações dependentes.

Os limites atuais continuam explícitos: sinais nomeados não carregam dados
personalizados; modelos são cópias; buscas arbitrárias de propriedades,
grupos/comentários visuais de nós, reroutes e bypass não estão disponíveis.
Teleporte entre cenas e viagem de grupos são trabalho futuro. Veja
[Smart Objects](../pt-BR/map-builder.md#portas-como-objetos-inteligentes) e
[o estado da implementação](../pt-BR/smart-objects-direction.md).

### Importação e exportação Universal VTT

- Importe `.uvtt`, `.dd2vtt` ou `.df2vtt` no formato **Universal VTT 0.2** com
  PNG ou WebP incorporado. Resolução, origem da grade, linhas de paredes,
  limites de portais e luzes viram uma nova cena nativa, inicialmente exclusiva
  do mestre. Origens fracionárias preservam o alinhamento da grade, e as paredes
  colineares são recortadas nas aberturas das portas.
- Exporte a cena nativa atual com fundo em tiles, imagens públicas, materiais
  dinâmicos ativos, geometria de paredes/portas e luzes habilitadas. Imagens de
  portas abertas respeitam seu pivô, e sprites/imagens de estado ajustados
  mantêm o tamanho exibido mesmo fora da faixa do editor comum de imagens.
- O importador valida estrutura, dimensões da imagem, números, propriedade dos
  recursos e limites de trabalho. Repetir a mesma importação retorna a cena já
  criada; falhas removem os tiles recém-gravados. A exportação apenas lê dados
  e exclui imagens exclusivas do mestre.
- Os avisos identificam diferenças do formato: interpretação de portais/janelas,
  cor ambiente, iluminação incorporada, sombras e valores de luz limitados ao
  intervalo nativo. Revise-os antes de transmitir um mapa importado ou baixar
  uma exportação.

Universal VTT gera uma cópia para intercâmbio. Ele não recupera um projeto do
Map Builder a partir de uma imagem final, nem preserva grafos, temporizadores,
tokens, cartas, permissões, névoa, desenhos ou áudio. Imagens individuais e
materiais dinâmicos viram pixels do fundo; trancas, apresentação secreta,
intervalos de altura e canais independentes de barreira não são preservados.
Mantenha a campanha e o projeto originais quando esses recursos forem necessários.
Veja [Universal VTT](../pt-BR/universal-vtt.md).

### Renderização da mesa, uploads e interface

- Luz e visão reutilizam índices limitados de paredes e resultados de oclusão.
  Cálculos maiores de visibilidade usam um module worker da mesma origem, com
  alternativa síncrona. Luzes animadas reutilizam texturas imutáveis; mapas de
  luz dos shaders usam a GPU, e a amostragem de partículas limita o trabalho de
  CPU. Recursos são liberados quando muda a cena ou o papel do observador. Isso
  não estabelece uma melhoria universal de FPS em GPUs físicas.
- Uploads de imagens de cena compartilham um pipeline limitado de tiles com
  Pillow/libvips, validando orientação, dimensões, pixels e quantidade de tiles.
  Ambos produzem WebP sem perdas. O extra opcional `vips` oferece libvips; os
  instaladores padrão mantêm Pillow disponível. `GRAVEWRIGHT_MAP_TILER=auto`
  usa libvips quando instalado e Pillow como alternativa. Mapas grandes ainda
  exigem memória, espaço temporário em disco e limites configurados adequados.
- Janelas nativas, diretórios, administração e o PDF System incluído usam
  espaçamento mais compacto e tokens consistentes, mantendo o texto da
  interface do host em pelo menos 12px. Textos dos documentos preservam seus
  tamanhos próprios. Itens, tipos e entradas de compêndio usam ordenação por
  idioma; criação, prévia e importação de compêndios mantêm suas permissões.
  Controles de upload de templates de ator ficam abaixo das ações principais e
  acima da busca.
- O workspace do Builder separa desenho do canvas, propriedades, camadas,
  persistência, importações e biblioteca. Ferramentas nativas, prévia e editores
  usam ES modules nomeados, compartilham Pixi e mantêm carregamento sob demanda.
  URLs públicas, compatibilidade do worker e verificação de outputs pelo Runner
  são preservados; chunks gerados sem uso são removidos. Mais requisições de
  módulos podem acrescentar custo a uma importação individual sem cache; essa
  refatoração não promete aceleração geral do início da aplicação.
- As correções abrangem tentativas de salvamento rejeitadas ou incertas,
  exclusão de áudio nas receitas de geração dinâmica, ajuste de decorações muito
  pequenas ou grandes, rotação de portas por Blueprint e entrega de sinais na
  cena atual. A recuperação do atualizador guarda uma cópia local de metadados
  antigos de release ativa quando o estado está ocioso e recusa reassociá-los
  enquanto houver atualização pendente.

Veja [renderização e organização do frontend](../pt-BR/frontend.md),
[configuração de tiles](../pt-BR/configuration.md#geração-de-tiles-e-imagens-grandes)
e [implantação](../pt-BR/deployment.md) para os requisitos de operação.

### Compatibilidade, migrações e dados

O SDK continua em **1.0.0**, sem alteração das versões dos contratos públicos
nesta atualização. A disponibilidade de recursos depende da versão do VTT;
compatibilidade com o SDK não acrescenta Map Builder ou Blueprints a hosts mais
antigos. Sistemas de RPG independentes continuam responsáveis por fichas,
regras, catálogos e imagens. O grupo de dependências libvips é opcional; a lista
obrigatória de dependências de execução não mudou.

**Esta atualização acrescenta seis migrações de banco.** As migrações de mapas `0008`
a `0013` criam armazenamento de projetos e histórico de geração, diagnósticos
de automação e trabalhos persistentes, restrições de temporizadores nomeados,
templates Blueprint da campanha e imagens geradas vinculadas à cena. Aplique
o fluxo normal de migração antes de iniciar o servidor atualizado. Não execute
código antigo sobre o banco migrado.

Antes de atualizar para 0.3.0, pare as escritas da aplicação e faça
backup conjunto de configuração, banco configurado, mídia privada, coleções de
conteúdo e extensões locais. Preserve `.env`, `data/` e caminhos definidos pelo
operador durante a substituição dos arquivos. Um rollback exige cópias
compatíveis de código e dados, além dos executáveis antigos. O armazenamento
padrão continua dentro de cada instalação descompactada.

Trabalhos Delay/Timer pendentes ficam no banco da instalação e são retomados
quando o worker ASGI está disponível, incluindo os vencidos após um reinício.
Exportações, snapshots e cópias de campanha excluem esses trabalhos; os logs de
automação também não entram nos pacotes da campanha. Eles não substituem um
backup consistente da instalação completa. Ao inspecionar uma cópia restaurada,
desabilite seu worker com `GRAVEWRIGHT_AUTOMATION_WORKER_ENABLED=false` até que
ela esteja pronta para executar os trabalhos pendentes.

Para projetos de builds intermediárias de desenvolvimento, o formato executável
atual de Blueprint é a versão 2. Ao carregar contêineres antigos, os grafos
descontinuados `onChange` e específicos de estado são descartados, preservando
elementos e sequências compatíveis. Mantenha um backup e revise esses
comportamentos antes de adotar o formato mais recente.

O [guia de testes](../pt-BR/testing.md) descreve suítes isoladas e cenários
nativos de instalação e atualização para contribuidores.

### Download e atualização

Use **`Gravewright-0.3.0-django.zip`** com seu arquivo de checksum correspondente,
**`Gravewright-0.3.0-django.zip.sha256`**, da tag **`v0.3.0`**.
O ZIP completo contém os instaladores de Windows, Linux e macOS.

Instalações na **0.2.3** podem atualizar para a **0.3.0** por
**Administração → Atualizações → Verificar atualizações**. Faça backup conjunto
de configuração e dados antes de iniciar a atualização, conforme descrito acima.

Na atualização manual, pare o Runner, substitua os arquivos da aplicação
preservando `.env`, `data/`, extensões locais e caminhos definidos pelo operador
e execute novamente o instalador da plataforma. O instalador prepara as
dependências fixadas e aplica o fluxo normal de migração. Instalações a partir
do código-fonte devem instalar as dependências fixadas e executar as migrações
antes de iniciar o servidor atualizado. Um rollback exige as cópias
compatíveis de código e dados.

O identificador de versão é `0.3.0`; o projeto continua no estágio **Alpha**.
Inglês permanece como idioma padrão da interface, e as preferências salvas do
host e das contas são preservadas.
