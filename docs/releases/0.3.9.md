# Gravewright 0.3.9 — Alpha

## Compendium modules

- A module can now supply compendiums without being a game system. It declares `content.compendiums` in its manifest like a system package, and needs no JavaScript `entry` when it only supplies content.
- A module for one system names it in `content.requiresSystem`, optionally with a range of that system's package versions such as `>=1.2.0 <2.0.0`. Its actor, item and spell packs use that system's document types. Without `requiresSystem`, a module supplies journal packs only and works in tables of every system.
- The GM activates a compendium module from the table's module list. Activation refuses a module for another system, or for a system version the table does not use, and checks every entry against the active system's registered actor and item types. The table's module list now explains why an activation failed instead of discarding the message.
- If a table later switches to a system version outside the module's range, the module stays selected but its packs are hidden until the GM fixes the selection; the server log records the reason. One unavailable package no longer hides the packs of the system or of other modules.
- Compendium files are still read only through the table's compendium permissions. Item and spell packs keep their player-readable default; actor and journal packs stay private to the GM until shared. Imported documents are copies that remain after the module is deactivated or removed.

## Journal compendiums

- Installed collections, from system packages and compendium modules, accept `journal_pack` packs. Entries use the `diary` (default), `quest`, `quest_board` or `roll_table` journal types and the native journal document format; a diary entry can instead provide plain text that becomes its first page on import.
- Journals imported from a pack are placed in folders named after the collection and the pack.

## One installed version per package

- The **Systems** and **Modules** libraries show one card per package. Installing another version of an installed package, from the catalog or from a local ZIP, replaces it the same way **Update** does: tables move to the new version, interface replacements and module storage are kept, an active language stays active and the old files are removed.
- In the installation browser, a newer catalog version of an installed package appears on that package's card as **Update available**, showing both versions, instead of a second **Install**.
- Installing an older version while a newer one is installed is refused; remove the installed package first. A package ID also cannot change its kind, for example from module to system or between a language package and an ordinary browser module. The same ID and version still cannot be installed with different contents.
- An active Django app switches versions after the supervised restart, as with Update. Revoked versions stay recorded so they cannot be installed again. The library shows the newest non-revoked release, or the newest revoked release if none remains usable.
- Installed cards show what a package provides: **Compendiums**, **For** followed by the system a compendium module requires, **Django · Server** and the catalog categories. Search also matches these tags.

See [Modules](../en/modules.md#compendiums-supplied-by-packages) and the [package library](../en/modules.md#package-library-and-installation-browser) for the manifest fields and error codes.

## Board rendering

- Drawing, moving or turning a card, and moving a spatial sound no longer rebuild the whole scene. Each part of the scene (images, door art, drawings, cards, lights, particles, shaders and darkness) refreshes from its own inputs, preserving the animation clock of lights, particles and shaders during these updates. A new stroke adds one object; a moved card keeps its object.
- Each light keeps its own shadow polygon. Opening or closing a door recalculates only the lights that reach that door; a switched-off light keeps its polygon for when it is switched on again. With at least 128 light-blocking wall segments, missing light polygons are calculated in a visibility worker when available; smaller scenes and unavailable workers use the same geometry on the interface thread.
- Token art is drawn as a single shape-clipped mesh that supports batching, removing each image's separate stencil mask. Condition badges are no longer recreated on every hover or selection.
- The new optional `GRAVEWRIGHT_MAP_TILE_QUALITY` setting (1–100) stores newly generated raster map tiles as lossy WebP. Empty, the default, keeps lossless tiles; solid-color maps stay lossless in either case. Restart the server to apply the setting; existing tiles are unchanged. See [Configuration](../en/configuration.md#map-tiling-and-large-images).

## Compatibility and migration

This release adds no database migrations relative to 0.3.8. The SDK version
remains `1.0.0`. The manifest schema now accepts `content` in modules without
`system`, plus the optional `content.requiresSystem`; hosts up to 0.3.8 refuse
to install such modules, so their authors should document 0.3.9 as the minimum
host. Existing system packages and their compendiums keep working unchanged.

Installing a different version now replaces the installed one. To return to an
older version, remove the newer package and install the older one; module
storage is not reverted. Installations that already have several versions of a
package show the newest non-revoked one, or the newest revoked one if necessary;
the next installation or update of that package
replaces the older versions and moves their tables to it.

## Português (Brasil)

### Módulos de compêndio

- Um módulo agora pode fornecer compêndios sem ser um sistema de jogo. Ele declara `content.compendiums` no manifesto, como um pacote de sistema, e não precisa de `entry` JavaScript quando só fornece conteúdo.
- Um módulo para um sistema indica esse sistema em `content.requiresSystem`, com uma faixa opcional de versões do pacote do sistema, como `>=1.2.0 <2.0.0`. Seus compêndios de atores, itens e magias usam os tipos de documento desse sistema. Sem `requiresSystem`, o módulo fornece apenas compêndios de diários e funciona em mesas de qualquer sistema.
- O mestre ativa um módulo de compêndio pela lista de módulos da mesa. A ativação recusa um módulo de outro sistema, ou de uma versão do sistema que a mesa não usa, e confere cada entrada com os tipos de ator e item registrados pelo sistema ativo. A lista de módulos da mesa agora explica por que uma ativação falhou, em vez de descartar a mensagem.
- Se a mesa passar depois para uma versão do sistema fora da faixa do módulo, ele continua selecionado, mas seus compêndios ficam ocultos até o mestre corrigir a seleção; o log do servidor registra o motivo. Um pacote indisponível não esconde mais os compêndios do sistema nem de outros módulos.
- Os arquivos de compêndio continuam sendo lidos apenas pelas permissões de compêndio da mesa. Compêndios de itens e magias mantêm a leitura liberada para jogadores por padrão; compêndios de atores e diários ficam privados do mestre até serem compartilhados. Documentos importados são cópias e permanecem depois que o módulo é desativado ou removido.

### Compêndios de diários

- Coleções instaladas, de pacotes de sistema e de módulos de compêndio, aceitam compêndios `journal_pack`. As entradas usam os tipos de diário `diary` (padrão), `quest`, `quest_board` ou `roll_table` e o formato nativo dos diários; uma entrada `diary` pode, em vez disso, trazer texto simples, que vira a primeira página na importação.
- Diários importados de um compêndio ficam em pastas com o nome da coleção e do compêndio.

### Uma versão instalada por pacote

- As bibliotecas de **Sistemas** e **Módulos** mostram um cartão por pacote. Instalar outra versão de um pacote instalado, pelo catálogo ou por um ZIP local, substitui a anterior como **Atualizar** faz: as mesas passam para a nova versão, substituições de interface e dados salvos do módulo são mantidos, um idioma ativo continua ativo e os arquivos antigos são removidos.
- Na janela de instalação, uma versão mais nova do catálogo para um pacote instalado aparece no cartão desse pacote como **Atualização disponível**, com as duas versões, em vez de um segundo **Instalar**.
- Instalar uma versão mais antiga enquanto há uma mais nova instalada é recusado; remova antes o pacote instalado. Um ID de pacote também não pode mudar de tipo, por exemplo de módulo para sistema ou entre pacote de idioma e módulo comum de navegador. O mesmo ID e versão continuam sem poder ser instalados com outro conteúdo.
- Um app Django ativo troca de versão após a reinicialização supervisionada, como em Atualizar. Versões revogadas continuam registradas para não poderem ser instaladas de novo. A biblioteca mostra a versão não revogada mais nova ou a versão revogada mais nova quando não resta uma utilizável.
- Os cartões instalados mostram o que o pacote oferece: **Compêndios**, **Para** seguido do sistema exigido por um módulo de compêndio, **Django · Servidor** e as categorias do catálogo. A busca também encontra essas etiquetas.

Consulte [Módulos](../pt-BR/modules.md#compêndios-fornecidos-por-pacotes) e a [biblioteca de pacotes](../pt-BR/modules.md#biblioteca-de-pacotes-e-instalação) para os campos do manifesto e os códigos de erro.

### Renderização do tabuleiro

- Desenhar, mover ou girar uma carta e mover um som espacial não reconstroem mais a cena inteira. Cada parte da cena (imagens, arte de portas, desenhos, cartas, luzes, partículas, shaders e escuridão) é atualizada a partir das próprias entradas, preservando o relógio de animação de luzes, partículas e shaders durante essas atualizações. Um traço novo acrescenta um objeto; uma carta movida mantém o seu.
- Cada luz guarda o próprio polígono de sombra. Abrir ou fechar uma porta recalcula apenas as luzes que alcançam essa porta; uma luz desligada guarda o polígono para quando for religada. Com pelo menos 128 segmentos de parede que bloqueiam luz, polígonos de luz ausentes são calculados em um worker de visibilidade quando disponível; cenas menores e workers indisponíveis usam a mesma geometria na thread da interface.
- A arte dos tokens é desenhada como uma única malha recortada no formato do token que permite agrupar chamadas de desenho, removendo a máscara de stencil separada de cada imagem. Os ícones de condição não são mais recriados a cada passagem do mouse ou seleção.
- A nova configuração opcional `GRAVEWRIGHT_MAP_TILE_QUALITY` (1–100) grava tiles de mapas raster gerados depois disso como WebP com perdas. Vazia, o padrão, mantém tiles sem perdas; mapas de cor sólida continuam sem perdas nos dois casos. Reinicie o servidor para aplicar a configuração; tiles existentes não mudam. Veja [Configuração](../pt-BR/configuration.md#geração-de-tiles-e-imagens-grandes).

### Compatibilidade e migração

Esta versão não acrescenta migrações de banco em relação à 0.3.8. A versão do SDK
permanece em `1.0.0`. O schema do manifesto agora aceita `content` em módulos sem
`system`, além do campo opcional `content.requiresSystem`; hosts até a 0.3.8
recusam instalar esses módulos, então seus autores devem indicar a 0.3.9 como
host mínimo. Pacotes de sistema existentes e seus compêndios continuam
funcionando sem alterações.

Instalar uma versão diferente agora substitui a instalada. Para voltar a uma
versão anterior, remova o pacote mais novo e instale o anterior; os dados salvos
do módulo não são revertidos. Instalações que já têm várias versões de um pacote
mostram a versão não revogada mais nova ou, se necessário, a revogada mais nova;
a próxima instalação ou atualização desse pacote substitui as versões antigas
e passa suas mesas para ela.

## Download and upgrade

Download `Gravewright-0.3.9-django.zip` and verify its accompanying SHA-256 file.
Managed installations can use Administration → Updates. For a manual upgrade,
stop the Runner, back up and preserve `.env`, `data/` and local extensions,
replace application files and rerun the platform installer to prepare assets and
apply migrations. Restart the server and reload connected browser tabs. With
SQLite WAL enabled, stop all database users before copying database files or use
the application's backup tools; never discard an active database's `-wal` or
`-shm` files. See [upgrade and recovery](../en/upgrading.md).

## Download e atualização

Baixe `Gravewright-0.3.9-django.zip` e confira o SHA-256. Instalações gerenciadas
podem usar Administração → Atualizações. Na atualização manual, pare o Runner,
faça backup e preserve `.env`, `data/` e extensões locais, substitua os arquivos
da aplicação e execute novamente o instalador para preparar os recursos e aplicar
as migrações. Reinicie o servidor e recarregue as abas conectadas. Com WAL ativo
no SQLite, pare todos os processos que usam o banco antes de copiar seus arquivos
ou utilize as ferramentas de backup da aplicação; nunca descarte os arquivos
`-wal` ou `-shm` de um banco ativo. Veja [atualização e recuperação](../pt-BR/upgrading.md).
