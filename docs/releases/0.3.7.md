# Gravewright 0.3.7 — Alpha

## Realtime performance

- Reduce repeated database queries when delivering scene cards and combat state. Token drag previews load only the requested tokens, and stationary tokens skip collision checks.
- Reduce browser copying when applying scene deltas while preserving independent state for consumers.
- Reuse audio listener positions, skip unnecessary spatial calculations and load walls only when an audible source needs an occlusion check.
- Send changed audio fields over the WebSocket instead of retransmitting unchanged catalogs. Native tools and modules continue to receive complete state, with resynchronization when needed.
- Revalidate presence authorization without rewriting a lease that is not yet due for renewal.
- Limit concurrent database reads for map layers, tokens, audio and combat to two per server event loop. Commands, transient samples and network sends remain outside this limit; access is checked after admission and before delivery, and disconnects retain the permit until the database work finishes.

`GRAVEWRIGHT_REALTIME_PROJECTION_CONCURRENCY` defaults to `2`; set it to `0` to disable the limit. Existing installations pick up the default without editing `.env`. This release preserves the public SDK and introduces no database migrations relative to 0.3.6.

## Measurements and validation

Isolated local comparisons measured a one-token player preview in a 1,000-token scene at 47.580 ms before and 3.334 ms after the change. A spatial-audio fixture with 12 listeners, 60 sources and 500 walls fell from 153.318 ms to 9.373 ms. With 10 simulated WebSocket clients, enabling the production read limit reduced the measured projection refresh p95 from 1,082.458 ms to 524.783 ms. These are operation-specific synthetic measurements, not guarantees for network latency or frame rate in every campaign. See the [measurement details](../en/realtime-direction.md).

The changes passed 296 focused Python tests, 28 JavaScript tests and an isolated audio lifecycle scenario with a GM and a player in real browser clients. Coverage includes permissions, revisions, state reconstruction and cancellation during pending reads.

## Português (Brasil)

### Desempenho em tempo real

- Reduz consultas repetidas ao entregar cartas da cena e o estado do combate. A prévia de arraste carrega apenas os tokens solicitados, e tokens parados dispensam testes de colisão.
- Reduz cópias no navegador ao aplicar alterações da cena, preservando estados independentes para quem os utiliza.
- Reutiliza posições dos ouvintes, evita cálculos espaciais desnecessários e carrega paredes somente quando uma fonte audível exige verificar oclusão.
- Envia apenas campos alterados do áudio pelo WebSocket, evitando retransmitir catálogos inalterados. Ferramentas nativas e módulos continuam recebendo o estado completo, com ressincronização quando necessário.
- Revalida a autorização da presença sem regravar uma concessão que ainda não precisa de renovação.
- Limita a duas as leituras simultâneas do banco para camadas, tokens, áudio e combate por loop de eventos do servidor. Comandos, amostras transitórias e envios de rede ficam fora desse limite; o acesso é conferido após a admissão e antes da entrega, e desconexões mantêm a vaga ocupada até a consulta terminar.

`GRAVEWRIGHT_REALTIME_PROJECTION_CONCURRENCY` tem valor padrão `2`; use `0` para desativar o limite. Instalações existentes recebem o padrão sem editar `.env`. A versão preserva o SDK público e não acrescenta migrações de banco em relação à 0.3.6.

### Medições e validação

Comparações locais isoladas mediram a prévia de um token de jogador em uma cena com 1.000 tokens: 47,580 ms antes e 3,334 ms depois. O cenário de áudio espacial com 12 ouvintes, 60 fontes e 500 paredes passou de 153,318 ms para 9,373 ms. Com 10 clientes WebSocket simulados, ativar o limite de leituras da implementação final reduziu o p95 de atualização das projeções de 1.082,458 ms para 524,783 ms. São medições sintéticas de operações específicas, sem garantia de latência de rede ou taxa de quadros para todas as campanhas. Consulte os [detalhes das medições](../pt-BR/realtime-direction.md).

Os ajustes passaram por 296 testes Python focados, 28 testes JavaScript e um cenário isolado do ciclo de áudio com mestre e jogador em navegadores reais. A cobertura inclui permissões, revisões, reconstrução do estado e cancelamento durante consultas pendentes.

## Download and upgrade

Download `Gravewright-0.3.7-django.zip` and verify its accompanying SHA-256 file. Managed installations can use Administration → Updates. For a manual upgrade, stop the Runner, back up and preserve `.env`, `data/` and local extensions, replace application files and rerun the platform installer. Restart the server and reload connected browser tabs to load the updated realtime transport. Use the normal installer migration workflow when upgrading older installations. With SQLite WAL enabled, stop all database users before copying database files or use the application's backup tools; never discard an active database's `-wal` or `-shm` files.

## Download e atualização

Baixe `Gravewright-0.3.7-django.zip` e confira o SHA-256. Instalações gerenciadas podem usar Administração → Atualizações. Na atualização manual, pare o Runner, faça backup e preserve `.env`, `data/` e extensões locais, substitua os arquivos da aplicação e execute novamente o instalador. Reinicie o servidor e recarregue as abas conectadas para carregar o transporte atualizado. Use o fluxo normal de migrações do instalador ao atualizar instalações mais antigas. Com WAL ativo no SQLite, pare todos os processos que usam o banco antes de copiar seus arquivos ou utilize as ferramentas de backup da aplicação; nunca descarte os arquivos `-wal` ou `-shm` de um banco ativo.
